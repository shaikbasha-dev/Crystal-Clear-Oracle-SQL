# 19.14-Complete-Revision

## 1. What is Normalisation?

**Normalisation** is a database design technique used to:

* Organize data properly into tables
* Reduce unnecessary data repetition (**redundancy**)
* Avoid data anomalies
* Improve data consistency and integrity

### Simple idea

Instead of keeping everything in one large table:

```text
STUDENT
---------------------------------------------------------
Student_ID | Student_Name | Course | Department | Hobbies
---------------------------------------------------------
101        | Basha        | Java   | CSE        | Cricket
101        | Basha        | Python | CSE        | Music
102        | Ravi         | Java   | ECE        | Cricket
```

we gradually organize the data into better-structured tables.

---

# 2. Why Do We Need Normalisation?

Without proper normalization, three major problems can occur:

| Anomaly            | Meaning                                                           |
| ------------------ | ----------------------------------------------------------------- |
| **Insert Anomaly** | Cannot insert some information independently                      |
| **Update Anomaly** | Same information must be changed in multiple places               |
| **Delete Anomaly** | Deleting one record may accidentally remove important information |

### Easy memory

> **Insert → Problem while adding**
> **Update → Problem while changing**
> **Delete → Problem while removing**

---

# 3. Complete Normal Forms

The normalization journey is:

```text
UNF
 ↓
1NF
 ↓
2NF
 ↓
3NF
 ↓
BCNF
 ↓
4NF
 ↓
5NF
```

Each normal form solves a particular type of problem.

| Normal Form | Main Concept                                |
| ----------- | ------------------------------------------- |
| **1NF**     | Atomic values                               |
| **2NF**     | Remove partial dependency                   |
| **3NF**     | Remove transitive dependency                |
| **BCNF**    | Every determinant must be a super key       |
| **4NF**     | Remove problematic multivalued dependencies |
| **5NF**     | Deal with join dependencies                 |

### ⭐ Most important interview memory

```text
1NF  → ATOMIC
2NF  → PARTIAL
3NF  → TRANSITIVE
BCNF → SUPER KEY
4NF  → MULTIVALUED
5NF  → JOIN
```

---

# 4. Keys Used in Normalisation

A **key** helps identify rows and is important when analyzing dependencies.

| Key               | Simple Meaning                                    |
| ----------------- | ------------------------------------------------- |
| **Super Key**     | Any set of columns that uniquely identifies a row |
| **Candidate Key** | Minimal super key                                 |
| **Primary Key**   | Candidate key selected as the main key            |
| **Alternate Key** | Candidate key not selected as primary             |
| **Composite Key** | Key made using two or more columns                |

### Example

```text
Student_ID
```

can uniquely identify a student.

For an enrollment table:

```text
Student_ID + Course_ID
```

may together identify one enrollment.

Therefore:

```text
(Student_ID, Course_ID)
```

is a **composite key**.

---

# 5. Functional Dependency

Functional dependency describes a relationship between attributes.

Notation:

```text
A → B
```

Read it as:

> **A determines B**

Example:

```text
Student_ID → Student_Name
```

Meaning:

> If we know Student_ID, we can determine the Student_Name.

### Important terms

```text
A → B

A = Determinant
B = Dependent
```

---

# 6. Types of Dependency

The important dependencies for normalization are:

### 1. Full Functional Dependency

The complete composite key is required to determine the attribute.

```text
(Student_ID, Course_ID) → Marks
```

Both values together determine Marks.

---

### 2. Partial Dependency

Only part of a composite key determines an attribute.

Example:

```text
(Student_ID, Course_ID) → Student_Name
```

But actually:

```text
Student_ID → Student_Name
```

Only part of the composite key is required.

That is **partial dependency**.

---

### 3. Transitive Dependency

A non-key attribute determines another non-key attribute.

Example:

```text
Student_ID → Department_ID
Department_ID → Department_Name
```

Therefore:

```text
Student_ID → Department_Name
```

This is a **transitive dependency**.

---

# 7. First Normal Form — 1NF

## Rule

A table is in **1NF** when:

* Values are atomic
* There are no repeating groups
* One cell contains one value

### ❌ Not 1NF

```text
Student_ID | Student_Name | Phone_Numbers
------------------------------------------
101        | Basha        | 9876, 8765
```

One cell contains multiple phone numbers.

### ✅ 1NF

```text
Student_ID | Student_Name | Phone
---------------------------------
101        | Basha        | 9876
101        | Basha        | 8765
```

Now each cell contains one value.

### Memory

> **1NF = One cell → One value**

**Important:** `NULL` by itself does not violate 1NF. The key idea is atomicity.

---

# 8. Second Normal Form — 2NF

## Rule

A table must:

1. Already be in **1NF**
2. Have **no partial dependency**

2NF is especially important when the table has a **composite key**.

Consider:

```text
(Student_ID, Course_ID) → Marks
Student_ID → Student_Name
Course_ID → Course_Name
```

The primary key is:

```text
(Student_ID, Course_ID)
```

But:

```text
Student_ID → Student_Name
```

uses only part of the key.

And:

```text
Course_ID → Course_Name
```

also uses only part of the key.

Therefore, partial dependencies exist.

### Decompose

```text
STUDENT
---------
Student_ID
Student_Name
```

```text
COURSE
---------
Course_ID
Course_Name
```

```text
ENROLLMENT
-----------
Student_ID
Course_ID
Marks
```

Now the partial dependencies are removed.

### Memory

> **2NF = 1NF + No Partial Dependency**

---

# 9. Third Normal Form — 3NF

## Rule

A table must:

1. Already be in **2NF**
2. Have **no transitive dependency**

Example:

```text
Student_ID → Department_ID
Department_ID → Department_Name
```

Therefore:

```text
Student_ID → Department_Name
```

The Student_ID indirectly determines Department_Name through Department_ID.

This is transitive dependency.

### Decompose

```text
STUDENT
-------------------------
Student_ID
Student_Name
Department_ID
```

```text
DEPARTMENT
-------------------------
Department_ID
Department_Name
```

Now Department_Name belongs to the Department table.

### Memory

> **3NF = 2NF + No Transitive Dependency**

---

# 10. BCNF

BCNF means:

> **Boyce-Codd Normal Form**

It is stricter than 3NF.

### Main rule

For every non-trivial functional dependency:

```text
X → Y
```

**X must be a Super Key.**

### Easy interview statement

> **Every determinant must be a Super Key.**

Example:

```text
Instructor → Course
```

If `Instructor` is not a super key, the relation violates BCNF.

The relation may need to be decomposed into separate tables.

### Relationship

```text
3NF
 ↓
Stricter condition
 ↓
BCNF
```

### Important

```text
BCNF ⇒ 3NF
```

But:

```text
3NF ⇏ BCNF
```

That means every BCNF relation satisfies 3NF, but every 3NF relation does not necessarily satisfy BCNF.

---

# 11. Fourth Normal Form — 4NF

4NF deals with **Multivalued Dependencies (MVDs)**.

Notation:

```text
A →→ B
```

Suppose a student has:

```text
Skills:
Java, Python

Hobbies:
Cricket, Music
```

If skills and hobbies are independent, storing them together can produce combinations:

```text
Student | Skill  | Hobby
-------------------------
101     | Java   | Cricket
101     | Java   | Music
101     | Python | Cricket
101     | Python | Music
```

This creates unnecessary combinations.

### Decompose

```text
STUDENT_SKILL
-------------
Student_ID
Skill
```

```text
STUDENT_HOBBY
-------------
Student_ID
Hobby
```

### Rule

For every non-trivial multivalued dependency:

```text
X →→ Y
```

X should be a super key.

### Memory

> **4NF = Multivalued Dependency**

---

# 12. Fifth Normal Form — 5NF

5NF is also called:

> **Project-Join Normal Form (PJ/NF)**

It deals with **Join Dependencies**.

The basic idea is that a relation should not be unnecessarily decomposable into smaller relations when the relationship can be represented correctly without loss.

A common conceptual example involves:

```text
Supplier
Product
Project
```

A complex three-way relationship may be decomposed into:

```text
Supplier_Product
Supplier_Project
Product_Project
```

The decomposition must preserve the required relationship correctly.

### Memory

> **5NF = Join Dependency**

5NF is much less commonly encountered in ordinary application development than 1NF, 2NF, 3NF, and BCNF.

---

# 13. Complete Comparison of Normal Forms

| Normal Form | Condition                                                      | Removes                                  |
| ----------- | -------------------------------------------------------------- | ---------------------------------------- |
| **1NF**     | Atomic values                                                  | Repeating groups / non-atomic values     |
| **2NF**     | 1NF + no partial dependency                                    | Partial dependency                       |
| **3NF**     | 2NF + no transitive dependency                                 | Transitive dependency                    |
| **BCNF**    | Every determinant is a super key                               | Certain dependency anomalies left by 3NF |
| **4NF**     | No problematic non-trivial MVD unless determinant is super key | Multivalued dependency                   |
| **5NF**     | No unnecessary lossless decomposition due to join dependency   | Join dependency                          |

---

# 14. Complete Normalisation Flow

Imagine we start with a badly organized table.

```text
STUDENT_COURSE
-------------------------------------------------------
Student_ID
Student_Name
Department_ID
Department_Name
Course_ID
Course_Name
Marks
Skills
Hobbies
```

We progressively improve it.

### Step 1 — 1NF

Make values atomic.

```text
Student_ID | Course_ID | Skill | Hobby
```

No multiple values inside one cell.

---

### Step 2 — 2NF

Remove partial dependencies.

```text
STUDENT
COURSE
ENROLLMENT
```

For example:

```text
Student_ID → Student_Name
Course_ID  → Course_Name
```

are moved to their appropriate tables.

---

### Step 3 — 3NF

Remove transitive dependencies.

```text
Student_ID → Department_ID
Department_ID → Department_Name
```

Create:

```text
DEPARTMENT
```

---

### Step 4 — BCNF

Check every determinant.

Ask:

> **Is every determinant a super key?**

If not, decompose where necessary.

---

### Step 5 — 4NF

Check for independent multivalued relationships.

For example:

```text
Student →→ Skill
Student →→ Hobby
```

Separate:

```text
STUDENT_SKILL
STUDENT_HOBBY
```

---

### Step 6 — 5NF

Check whether complex join dependencies require further decomposition.

---

# 16. Normalisation vs Denormalisation

| Feature             | Normalisation                | Denormalisation                         |
| ------------------- | ---------------------------- | --------------------------------------- |
| Redundancy          | Reduces                      | May intentionally increase              |
| Number of tables    | Usually increases            | May decrease                            |
| Joins               | May require more joins       | May require fewer joins                 |
| Data consistency    | Generally easier to maintain | More care required                      |
| Storage duplication | Lower                        | Higher                                  |
| Read performance    | May require more joins       | Can improve some read-heavy workloads   |
| Main purpose        | Good structure and integrity | Selective performance/read optimization |

### Simple understanding

**Normalisation:**

> Split data properly to reduce repetition.

**Denormalisation:**

> Intentionally keep some repeated/combined data when there is a good reason, often to reduce joins or improve read performance.

Denormalisation is **not automatically bad**. It should be deliberate and justified by the workload.

---

# 17. Advantages of Normalisation

### 1. Reduces redundancy

The same information does not need to be stored repeatedly.

### 2. Reduces anomalies

Helps prevent:

* Insert anomaly
* Update anomaly
* Delete anomaly

### 3. Improves consistency

A piece of information generally has one proper place.

### 4. Improves integrity

Relationships between entities can be represented more clearly.

### 5. Better database structure

Each table has a clearer responsibility.

---

# 18. Disadvantages of Normalisation

### 1. More tables

Highly normalized databases can contain many tables.

### 2. More joins

Retrieving related information may require joins.

### 3. Queries can become more complex

Especially when information is distributed across several tables.

### 4. Some read workloads may require more work

Applications that frequently need large combined datasets may perform more joins.

---

# 19. When Should We Use Normalisation?

Normalization is generally useful when:

* Data changes frequently
* Data consistency is important
* Transactions are important
* We want to minimize duplication
* Database integrity is a priority

For read-heavy/reporting workloads, selective denormalization may sometimes be useful.

# 20. Most Important Differences

## 1NF vs 2NF

| 1NF                                        | 2NF                        |
| ------------------------------------------ | -------------------------- |
| Atomic values                              | No partial dependency      |
| Removes repeating groups/non-atomic values | Removes partial dependency |
| First step                                 | Comes after 1NF            |

### Memory

```text
1NF → Atomic
2NF → Partial
```

---

## 2NF vs 3NF

| 2NF                           | 3NF                                                            |
| ----------------------------- | -------------------------------------------------------------- |
| Removes partial dependency    | Removes transitive dependency                                  |
| Important with composite keys | Can apply even when transitive dependency exists independently |
| Requires 1NF                  | Requires 2NF                                                   |

### Memory

```text
2NF → Partial
3NF → Transitive
```

---

## 3NF vs BCNF

| 3NF                                                                              | BCNF                                         |
| -------------------------------------------------------------------------------- | -------------------------------------------- |
| Less strict                                                                      | More strict                                  |
| Allows certain cases where determinant isn't a super key under the 3NF condition | Requires every determinant to be a super key |
| Every BCNF relation is 3NF                                                       | Not every 3NF relation is BCNF               |

---

## BCNF vs 4NF

| BCNF                                         | 4NF                                 |
| -------------------------------------------- | ----------------------------------- |
| Deals primarily with functional dependencies | Deals with multivalued dependencies |
| Determinant must be super key                | MVD determinant must be super key   |
| `X → Y`                                      | `X →→ Y`                            |

---

## 4NF vs 5NF

| 4NF                                        | 5NF                                      |
| ------------------------------------------ | ---------------------------------------- |
| Multivalued dependencies                   | Join dependencies                        |
| Handles independent multiple relationships | Handles complex decompositions and joins |
| `X →→ Y`                                   | Join dependency                          |

---

# 21. Important Interview Questions — Quick Revision

### Q1. What is normalization?

Normalization is a database design technique used to organize data, reduce redundancy, and avoid insert, update, and delete anomalies.

---

### Q2. What is 1NF?

A table is in 1NF when its values are atomic and there are no repeating groups.

**Memory:** Atomic.

---

### Q3. What is 2NF?

A table is in 2NF when it is in 1NF and has no partial functional dependency.

**Memory:** Partial.

---

### Q4. What is 3NF?

A table is in 3NF when it is in 2NF and has no transitive functional dependency.

**Memory:** Transitive.

---

### Q5. What is BCNF?

BCNF requires every determinant of a non-trivial functional dependency to be a super key.

**Memory:** Super Key.

---

### Q6. What is 4NF?

4NF deals with multivalued dependencies and requires the determinant of a non-trivial MVD to be a super key.

**Memory:** Multivalued.

---

### Q7. What is 5NF?

5NF, or Project-Join Normal Form, deals with join dependencies and unnecessary decompositions.

**Memory:** Join.

---

### Q8. Which normal form removes partial dependency?

**2NF**

---

### Q9. Which normal form removes transitive dependency?

**3NF**

---

### Q10. Which is stricter, 3NF or BCNF?

**BCNF**

---

### Q11. Can a table be in 3NF but not BCNF?

**Yes.**

BCNF is stricter than 3NF.

---

### Q12. Can partial dependency exist with a single-column primary key?

**No.**

Partial dependency requires a composite key because "partial" means depending on only part of a key.

---

### Q13. What is functional dependency?

A functional dependency describes how one attribute or set of attributes determines another.

```text
A → B
```

means A determines B.

---

### Q14. What is a composite key?

A key formed using two or more columns.

Example:

```text
(Student_ID, Course_ID)
```

---

### Q15. What is denormalization?

Denormalization is the deliberate introduction of some redundancy or combination of data to reduce joins or improve certain read-heavy workloads.

---

# 22. Scenario-Based Identification

If an interviewer gives you a situation, identify the normal form problem.

### Situation 1

```text
Phone = 9876, 8765
```

One cell has multiple values.

**Answer: 1NF violation**

---

### Situation 2

```text
(Student_ID, Course_ID) → Marks

Student_ID → Student_Name
```

Only part of the composite key determines Student_Name.

**Answer: 2NF / Partial Dependency**

---

### Situation 3

```text
Student_ID → Department_ID
Department_ID → Department_Name
```

Student_ID indirectly determines Department_Name.

**Answer: 3NF / Transitive Dependency**

---

### Situation 4

```text
Instructor → Course
```

but Instructor is not a super key.

**Answer: BCNF violation**

---

### Situation 5

A student has independent:

```text
Skills
Hobbies
```

and combining them creates unnecessary combinations.

**Answer: 4NF / Multivalued Dependency**

---

### Situation 6

A complex relationship can be represented through several smaller relations, and the correctness of the decomposition depends on a join dependency.

**Answer: 5NF**

---

# 23. The Golden Memory Trick ⭐

Remember these six words:

```text
1NF  → ATOMIC
2NF  → PARTIAL
3NF  → TRANSITIVE
BCNF → SUPER KEY
4NF  → MULTIVALUED
5NF  → JOIN
```

Or remember:

> **Atomic → Partial → Transitive → Super Key → Multivalued → Join**

This sequence is extremely useful for interviews.

# 24. One Complete Interview Answer

If the interviewer asks:

> **"Explain normalization."**

You can answer:

> **Normalization is a database design technique used to organize data into properly structured tables, reduce redundancy, and avoid insert, update, and delete anomalies. It is performed through different normal forms. 1NF ensures atomic values, 2NF removes partial dependency, 3NF removes transitive dependency, BCNF requires every determinant to be a super key, 4NF deals with multivalued dependencies, and 5NF deals with join dependencies.**

That is a strong concise interview answer.
