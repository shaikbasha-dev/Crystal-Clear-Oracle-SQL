# 19.5-Second-Normal-Form-2NF

## 1. What is 2NF?

**2NF (Second Normal Form)** is the second level of normalization.

A table is in **2NF** when:

1. The table is already in **1NF**.
2. There is **no Partial Functional Dependency**.

### Simple definition

> **2NF = 1NF + No Partial Dependency**

The most important point is:

> A non-key attribute should depend on the **whole composite key**, not just a part of it.

---

# 2. First Understand the Problem

Consider this table:

| Student_ID | Course_ID | Student_Name | Course_Name | Marks |
| ---------: | --------- | ------------ | ----------- | ----: |
|        101 | C01       | Ravi         | Java        |    80 |
|        101 | C02       | Ravi         | Python      |    90 |
|        102 | C01       | Anil         | Java        |    75 |
|        102 | C02       | Anil         | Python      |    85 |

Assume the primary key is:

```text
(Student_ID, Course_ID)
```

Why?

Because:

* `Student_ID` alone is not unique.
* `Course_ID` alone is not unique.
* Together, they identify one student taking one course.

So:

```text
Primary Key = (Student_ID, Course_ID)
```

---

# 3. Find the Functional Dependencies

Now examine the columns.

### Student_Name

If we know:

```text
Student_ID = 101
```

we know:

```text
Student_Name = Ravi
```

Therefore:

```text
Student_ID → Student_Name
```

Notice something important:

`Student_Name` depends only on **Student_ID**.

But `Student_ID` is only **part of the composite key**:

```text
(Student_ID, Course_ID)
       ↑
   only one part
```

Therefore, this is a **Partial Functional Dependency**.

---

### Course_Name

Similarly:

```text
Course_ID → Course_Name
```

`Course_Name` depends only on `Course_ID`.

Again, `Course_ID` is only part of the composite key.

Therefore, this is also a **Partial Functional Dependency**.

---

### Marks

Now consider `Marks`.

A student's marks depend on **which student** and **which course**.

Therefore:

```text
(Student_ID, Course_ID) → Marks
```

Both parts of the composite key are required.

So `Marks` has a **Full Functional Dependency**.

---

# 4. What is Partial Functional Dependency?

A **Partial Functional Dependency** occurs when a non-key attribute depends on **only a part of a composite key**.

### Example

Composite key:

```text
(Student_ID, Course_ID)
```

Dependency:

```text
Student_ID → Student_Name
```

`Student_Name` depends only on:

```text
Student_ID
```

not on:

```text
Student_ID + Course_ID
```

Therefore:

```text
Partial Dependency
```

### Memory trick

> **Part of composite key → Partial Dependency**

---

# 5. Why is Partial Dependency a Problem?

Look at the original table:

| Student_ID | Course_ID | Student_Name | Course_Name | Marks |
| ---------: | --------- | ------------ | ----------- | ----: |
|        101 | C01       | Ravi         | Java        |    80 |
|        101 | C02       | Ravi         | Python      |    90 |
|        102 | C01       | Anil         | Java        |    75 |
|        102 | C02       | Anil         | Python      |    85 |

`Ravi` is repeated.

`Anil` is repeated.

`Java` is repeated.

`Python` is repeated.

The student information depends only on `Student_ID`.

The course information depends only on `Course_ID`.

They don't need to be repeated for every student-course combination.

---

# 6. How Does 2NF Solve This?

We separate the information into different tables.

### STUDENT

| Student_ID | Student_Name |
| ---------: | ------------ |
|        101 | Ravi         |
|        102 | Anil         |

### COURSE

| Course_ID | Course_Name |
| --------- | ----------- |
| C01       | Java        |
| C02       | Python      |

### ENROLLMENT

| Student_ID | Course_ID | Marks |
| ---------: | --------- | ----: |
|        101 | C01       |    80 |
|        101 | C02       |    90 |
|        102 | C01       |    75 |
|        102 | C02       |    85 |

Now:

```text
Student_ID → Student_Name
Course_ID  → Course_Name
(Student_ID, Course_ID) → Marks
```

Each non-key attribute is placed with the key it actually depends on.

The partial dependencies have been removed.

---

# 7. Visual Understanding

### Before 2NF

```text
              STUDENT_COURSE
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
 Student_ID       Course_ID       Marks
       │             │
       ↓             ↓
Student_Name     Course_Name
```

Problem:

```text
Student_Name ← Student_ID
Course_Name  ← Course_ID
```

Both depend on only **part of the composite key**.

---

### After 2NF

```text
       STUDENT
          │
     Student_ID
          │
          ↓
    Student_Name


       COURSE
          │
      Course_ID
          │
          ↓
     Course_Name


      ENROLLMENT
       /       \
Student_ID   Course_ID
       \       /
         Marks
```

Now `Marks` depends on the complete key:

```text
(Student_ID, Course_ID)
```

# 8. SQL Example

## Question

Create the student table separately so that student information does not depend partially on the enrollment composite key.

### Answer / Query

```sql
CREATE TABLE Student
(
    Student_ID   NUMBER PRIMARY KEY,
    Student_Name VARCHAR2(30)
);
```

This table stores information that depends on `Student_ID`.

---

## Question

Create the course table separately so that course information does not depend partially on the enrollment composite key.

### Answer / Query

```sql
CREATE TABLE Course
(
    Course_ID   VARCHAR2(10) PRIMARY KEY,
    Course_Name VARCHAR2(30)
);
```

This table stores information that depends on `Course_ID`.

---

## Question

Create an enrollment table where marks depend on the complete combination of student and course.

### Answer / Query

```sql
CREATE TABLE Enrollment
(
    Student_ID NUMBER,
    Course_ID  VARCHAR2(10),
    Marks      NUMBER,

    PRIMARY KEY (Student_ID, Course_ID),

    FOREIGN KEY (Student_ID)
        REFERENCES Student(Student_ID),

    FOREIGN KEY (Course_ID)
        REFERENCES Course(Course_ID)
);
```

Here:

```text
(Student_ID, Course_ID)
```

is the composite primary key.

And:

```text
(Student_ID, Course_ID) → Marks
```

is a full functional dependency.

# 10. How to Check Whether a Table is in 2NF

Follow these steps:

### Step 1 — Check 1NF

Ask:

> Is the table already in 1NF?

If **No**, it cannot be in 2NF.

---

### Step 2 — Find the Primary Key

Determine whether the primary key is:

```text
Single-column key
```

or:

```text
Composite key
```

---

### Step 3 — Find Functional Dependencies

Check what each non-key attribute depends on.

---

### Step 4 — Look for Partial Dependency

If a non-key attribute depends on only **part of a composite key**, then:

```text
❌ Not in 2NF
```

If no such dependency exists:

```text
✅ In 2NF
```

---

# 11. Important Point About Single-Column Primary Keys

Suppose a table has:

```text
Primary Key = Student_ID
```

There is no "part" of the key because the key contains only one attribute.

Therefore, **partial dependency cannot occur with a single-attribute primary key**.

So, if the table is already in 1NF and has a single-column primary key, it satisfies the 2NF requirement regarding partial dependency.

### Memory trick

```text
Composite Key
     ↓
Check Partial Dependency
     ↓
Important for 2NF
```

---

# 12. 1NF vs 2NF

| 1NF                          | 2NF                                        |
| ---------------------------- | ------------------------------------------ |
| First level of normalization | Second level                               |
| Requires atomic values       | Requires 1NF first                         |
| Removes repeating groups     | Removes partial dependency                 |
| One value per cell           | Non-key attributes depend on the whole key |
| Focuses on atomicity         | Focuses on dependency on composite keys    |

### Easy memory

```text
1NF → One cell = One value

2NF → Whole key = Dependency
```

---

# 13. Full vs Partial Dependency

| Full Functional Dependency                 | Partial Functional Dependency         |
| ------------------------------------------ | ------------------------------------- |
| Depends on the complete composite key      | Depends on only part of composite key |
| Example: `(Student_ID, Course_ID) → Marks` | Example: `Student_ID → Student_Name`  |
| Required for 2NF                           | Removed by 2NF                        |

### Very important

```text
(Student_ID, Course_ID) → Marks
             ↓
        FULL DEPENDENCY
```

But:

```text
Student_ID → Student_Name
       ↓
Only part of composite key
       ↓
PARTIAL DEPENDENCY
```

---

# 14. Common Confusion

### ❌ "2NF means there should be no duplicate values."

Not exactly.

Duplicate values can still exist in a properly normalized table.

The important rule is **removing partial functional dependency**.

---

### ❌ "2NF removes all redundancy."

No.

2NF specifically deals with **partial dependency**.

There can still be **transitive dependency**, which is addressed by **3NF**.

---

### ❌ "Every table must have a composite key for 2NF."

No.

A table can have a single-column primary key.

Partial dependency is specifically relevant when the key is composite.

---

# 15. Interview Questions

### Q1. What is 2NF?

**Answer:**

> 2NF is the second normal form. A table must first be in 1NF, and every non-key attribute must depend on the entire candidate key, not just a part of a composite key.

### Q2. What is the main condition for 2NF?

**Answer:**

```text
1NF + No Partial Functional Dependency
```

### Q3. What is partial dependency?

**Answer:**

> Partial dependency occurs when a non-key attribute depends on only a part of a composite key.

### Q4. Which normal form removes partial dependency?

**Answer:**

**2NF.**

### Q5. Can partial dependency occur with a single-column primary key?

**Answer:**

No. Partial dependency requires a composite key because there must be a "part" of the key.

### Q6. Does 2NF remove transitive dependency?

**Answer:**

No. Transitive dependency is addressed by **3NF**.

---

# 16. Interview-Ready Answer

> **Second Normal Form (2NF) is achieved when a table is already in 1NF and has no partial functional dependency. This means every non-key attribute must depend on the entire candidate key, not just a part of a composite key. 2NF mainly deals with partial dependencies that occur when a table has a composite key.**
