# 19.3-Keys-and-Functional-Dependency

Before learning **1NF, 2NF, and 3NF**, we need to understand two important ideas:

1. **Keys**
2. **Functional Dependency**

These concepts help us understand **why a table needs to be divided during normalization**.

---

# 1. What is a Key?

A **key** is an attribute or a combination of attributes that helps us **uniquely identify a row** in a table.

### Example

Consider a `STUDENT` table:

| Student_ID | Student_Name | Course |
| ---------- | ------------ | ------ |
| 101        | Ravi         | Java   |
| 102        | Anil         | Python |
| 103        | Sara         | SQL    |

Here:

```text
Student_ID
```

uniquely identifies each student.

So `Student_ID` can be used as a **key**.

---

# 2. Why Do We Need Keys?

Suppose we have:

| Student_ID | Student_Name |
| ---------- | ------------ |
| 101        | Ravi         |
| 102        | Anil         |
| 103        | Ravi         |

`Student_Name` cannot uniquely identify a student because two students can have the same name.

But:

```text
101
102
103
```

are unique.

Therefore, `Student_ID` is a better choice for identifying students.

### Simple memory

> **Key = Something that helps identify a row uniquely.**

---

# 3. Important Types of Keys

For normalization, the most important keys to understand are:

| Key               | Meaning                                                                   |
| ----------------- | ------------------------------------------------------------------------- |
| **Super Key**     | Any attribute or combination of attributes that uniquely identifies a row |
| **Candidate Key** | Minimal super key                                                         |
| **Primary Key**   | Candidate key selected to uniquely identify rows                          |
| **Alternate Key** | Candidate key not selected as primary key                                 |
| **Composite Key** | Key made from two or more attributes                                      |

---

# 4. Super Key

A **Super Key** is an attribute or combination of attributes that can uniquely identify a row.

Consider:

| Student_ID | Email                                   | Student_Name |
| ---------- | --------------------------------------- | ------------ |
| 101        | [ravi@gmail.com](mailto:ravi@gmail.com) | Ravi         |
| 102        | [anil@gmail.com](mailto:anil@gmail.com) | Anil         |
| 103        | [sara@gmail.com](mailto:sara@gmail.com) | Sara         |

Possible super keys include:

```text
Student_ID
Email
Student_ID + Student_Name
Student_ID + Email
Email + Student_Name
```

Why?

Because each combination can still uniquely identify the student.

But some of these contain **unnecessary attributes**.

That leads us to Candidate Key.

---

# 5. Candidate Key

A **Candidate Key** is a **minimal Super Key**.

"Minimal" means:

> We cannot remove any attribute from the key and still uniquely identify the row.

In our example:

```text
Student_ID
Email
```

can each uniquely identify a student.

Therefore, both can be candidate keys.

```text
Student_ID → Candidate Key
Email      → Candidate Key
```

But:

```text
Student_ID + Student_Name
```

is not a candidate key because `Student_ID` alone is already sufficient.

---

# 6. Primary Key

When there are multiple candidate keys, one candidate key is selected as the **Primary Key**.

For example:

```text
Candidate Keys:
    Student_ID
    Email
```

If we choose:

```text
Student_ID
```

as the primary key:

```text
Primary Key = Student_ID
Alternate Key = Email
```

---

# 7. Alternate Key

An **Alternate Key** is a candidate key that was **not selected as the primary key**.

Example:

```text
Candidate Keys:
    Student_ID
    Email

Selected Primary Key:
    Student_ID

Remaining Candidate Key:
    Email
```

Therefore:

```text
Email = Alternate Key
```

---

# 8. Composite Key

Sometimes a single column cannot uniquely identify a row.

In that situation, we can use **two or more columns together**.

Consider:

| Student_ID | Course_ID | Marks |
| ---------- | --------- | ----: |
| 101        | C01       |    80 |
| 101        | C02       |    90 |
| 102        | C01       |    75 |
| 102        | C02       |    85 |

Here:

```text
Student_ID
```

alone is not unique.

`101` occurs twice.

Similarly:

```text
Course_ID
```

alone is not unique.

`C01` occurs twice.

But:

```text
Student_ID + Course_ID
```

uniquely identifies each row.

Therefore:

```text
(Student_ID, Course_ID)
```

is a **Composite Key**.

---

# 9. Key Relationships

A simple way to remember the important keys:

```text
SUPER KEY
    ↓
Remove unnecessary attributes
    ↓
CANDIDATE KEY
    ↓
Choose one
    ↓
PRIMARY KEY

Other candidate keys
    ↓
ALTERNATE KEYS
```

A composite key is different in nature:

```text
COMPOSITE KEY
    ↓
Key containing 2 or more attributes
```

---

# 10. What is Functional Dependency?

Now comes the most important concept for normalization.

A **Functional Dependency** describes a relationship between attributes where the value of one attribute determines the value of another attribute.

It is written as:

```text
A → B
```

and read as:

> **A determines B**

---

# 11. Simple Example of Functional Dependency

Consider:

| Student_ID | Student_Name |
| ---------- | ------------ |
| 101        | Ravi         |
| 102        | Anil         |
| 103        | Sara         |

If we know:

```text
Student_ID = 101
```

we can determine:

```text
Student_Name = Ravi
```

Therefore:

```text
Student_ID → Student_Name
```

This means:

> Student_ID determines Student_Name.

---

# 12. Why Does This Dependency Exist?

Because `Student_ID` uniquely identifies a student.

If:

```text
Student_ID = 101
```

there should be only one corresponding student name.

Therefore:

```text
Student_ID → Student_Name
```

---

# 13. Another Example

Consider:

| Course_ID | Course_Name | Professor |
| --------- | ----------- | --------- |
| C01       | Java        | Kumar     |
| C02       | Python      | Priya     |
| C03       | SQL         | Ahmed     |

Here:

```text
Course_ID → Course_Name
```

and:

```text
Course_ID → Professor
```

Because knowing the `Course_ID` tells us which course and professor it represents.

---

# 14. Functional Dependency Notation

Suppose we have:

```text
Student_ID → Student_Name
```

We call:

```text
Student_ID
```

the **determinant**.

And:

```text
Student_Name
```

is the **dependent attribute**.

### Structure

```text
Determinant
     ↓
Student_ID  ─────────→  Student_Name
                          ↑
                       Dependent
```

---

# 15. Functional Dependency and Keys

This relationship is very important for normalization.

Suppose:

```text
Student_ID = Primary Key
```

and:

```text
Student_ID → Student_Name
Student_ID → Email
Student_ID → Phone
```

The primary key determines the student's other attributes.

So we can write:

```text
Student_ID → Student_Name, Email, Phone
```

This tells us that the student's details depend on the student's ID.

---

# 16. Full Functional Dependency

A **Full Functional Dependency** occurs when an attribute depends on the **entire key**, not just a part of a composite key.

This becomes especially important in **2NF**.

Consider:

| Student_ID | Course_ID | Marks |
| ---------- | --------- | ----: |
| 101        | C01       |    80 |
| 101        | C02       |    90 |
| 102        | C01       |    75 |

Primary key:

```text
(Student_ID, Course_ID)
```

`Marks` depends on both:

```text
Student_ID + Course_ID
```

because marks represent a particular student's marks in a particular course.

Therefore:

```text
(Student_ID, Course_ID) → Marks
```

This is a **Full Functional Dependency**.

---

# 17. Partial Functional Dependency

A **Partial Functional Dependency** occurs when a non-key attribute depends on **only part of a composite key**.

Consider:

| Student_ID | Course_ID | Student_Name | Marks |
| ---------- | --------- | ------------ | ----: |
| 101        | C01       | Ravi         |    80 |
| 101        | C02       | Ravi         |    90 |
| 102        | C01       | Anil         |    75 |

Composite primary key:

```text
(Student_ID, Course_ID)
```

But:

```text
Student_ID → Student_Name
```

`Student_Name` depends only on `Student_ID`, not on the complete composite key.

Therefore:

```text
(Student_ID, Course_ID) → Student_Name
```

is not a full dependency.

It is a **Partial Functional Dependency**.

### Why is this important?

Because **2NF removes partial functional dependencies**.

---

# 18. Transitive Functional Dependency

A **Transitive Dependency** occurs when a non-key attribute depends on another non-key attribute.

Example:

| Student_ID | Student_Name | Department_ID | Department_Name  |
| ---------- | ------------ | ------------- | ---------------- |
| 101        | Ravi         | D01           | Computer Science |
| 102        | Anil         | D01           | Computer Science |
| 103        | Sara         | D02           | Mathematics      |

We have:

```text
Student_ID → Department_ID
```

and:

```text
Department_ID → Department_Name
```

Therefore:

```text
Student_ID → Department_Name
```

through `Department_ID`.

This is called a **Transitive Dependency**.

### Why is this important?

Because **3NF removes transitive dependency**.

---

# 19. Three Dependencies You Must Remember

| Dependency                     | Simple meaning                                         | Important for  |
| ------------------------------ | ------------------------------------------------------ | -------------- |
| **Full Functional Dependency** | Depends on the complete key                            | 2NF            |
| **Partial Dependency**         | Depends on only part of a composite key                | Removed by 2NF |
| **Transitive Dependency**      | Non-key attribute depends on another non-key attribute | Removed by 3NF |

### Memory trick

```text
2NF → Remove PARTIAL dependency
3NF → Remove TRANSITIVE dependency
```

---

# 20. Key + Functional Dependency Example

Consider:

| Student_ID | Course_ID | Student_Name | Course_Name | Marks |
| ---------- | --------- | ------------ | ----------- | ----: |
| 101        | C01       | Ravi         | Java        |    80 |
| 101        | C02       | Ravi         | Python      |    90 |
| 102        | C01       | Anil         | Java        |    75 |

Primary key:

```text
(Student_ID, Course_ID)
```

Functional dependencies:

```text
Student_ID → Student_Name

Course_ID → Course_Name

(Student_ID, Course_ID) → Marks
```

Now observe:

### Student name

```text
Student_ID → Student_Name
```

Only part of the composite key determines it.

Therefore, this is a **partial dependency**.

### Course name

```text
Course_ID → Course_Name
```

Again, only part of the composite key determines it.

Therefore, this is also a **partial dependency**.

### Marks

```text
(Student_ID, Course_ID) → Marks
```

Both parts of the key are required.

Therefore, `Marks` has a **full functional dependency**.

This is exactly the type of dependency analysis we use when moving toward **2NF**.

---

# 21. Important Difference: Key vs Functional Dependency

| Key                         | Functional Dependency                      |
| --------------------------- | ------------------------------------------ |
| Used to identify rows       | Describes relationships between attributes |
| Can uniquely identify a row | Shows which attribute determines another   |
| Example: `Student_ID`       | Example: `Student_ID → Student_Name`       |
| Used to identify records    | Used to understand data relationships      |

### Simple way

```text
KEY
↓
Who is this row?

FUNCTIONAL DEPENDENCY
↓
Which attribute determines which other attribute?
```

# 22. Interview Questions

### Q1. What is a key?

A key is an attribute or combination of attributes used to uniquely identify a row in a table.

### Q2. What is a Super Key?

A Super Key is an attribute or combination of attributes that uniquely identifies a row.

### Q3. What is a Candidate Key?

A Candidate Key is a **minimal Super Key**.

### Q4. What is a Primary Key?

A Primary Key is the Candidate Key selected to uniquely identify rows in a table.

### Q5. What is an Alternate Key?

An Alternate Key is a Candidate Key that was not selected as the Primary Key.

### Q6. What is a Composite Key?

A Composite Key is a key consisting of **two or more attributes**.

### Q7. What is Functional Dependency?

Functional Dependency is a relationship in which one attribute determines another attribute.

It is represented as:

```text
A → B
```

### Q8. What is Partial Dependency?

Partial Dependency occurs when a non-key attribute depends on only part of a composite key.

### Q9. What is Transitive Dependency?

Transitive Dependency occurs when a non-key attribute depends on another non-key attribute.

### Q10. Which normal form removes Partial Dependency?

**2NF.**

### Q11. Which normal form removes Transitive Dependency?

**3NF.**
