# 19.9-Fifth-Normal-Form-5NF

## 1. What is 5NF?

**5NF (Fifth Normal Form)** is also called **Project-Join Normal Form (PJ/NF)**.

It is a higher level of database normalization that deals mainly with **Join Dependencies**.

### Simple definition

> **5NF ensures that a table cannot be further decomposed into smaller tables without losing information or creating incorrect information when the tables are joined back together.**

In simple words:

> **5NF removes redundancy caused by complex relationships involving three or more tables.**

---

# 2. What Problem Does 5NF Solve?

Suppose we have three entities:

```text
SUPPLIER
PRODUCT
PROJECT
```

And suppose a business relationship says:

> A supplier supplies a particular product to a particular project.

We could store everything in one table:

| Supplier | Product | Project |
| -------- | ------- | ------- |
| S1       | P1      | PR1     |
| S1       | P2      | PR1     |
| S2       | P1      | PR1     |

Here each row represents a **three-way relationship**:

```text
Supplier + Product + Project
```

Sometimes such a relationship can actually be represented by several smaller relationships.

5NF helps determine whether such decomposition is possible **without changing the meaning of the data**.

---

# 3. What is Join Dependency?

A **Join Dependency** means that a table can be reconstructed by joining two or more smaller tables.

It is commonly represented conceptually as:

```text id="w3d7km"
*(R1, R2, R3)
```

The important idea is:

> A relation contains a complex relationship that can be represented by multiple smaller relations, and joining those relations should recreate the original valid relationship.

---

# 4. Simple Example

Suppose we have:

### SUPPLIER_PRODUCT

| Supplier | Product |
| -------- | ------- |
| S1       | P1      |
| S1       | P2      |
| S2       | P1      |

### SUPPLIER_PROJECT

| Supplier | Project |
| -------- | ------- |
| S1       | PR1     |
| S2       | PR1     |

### PRODUCT_PROJECT

| Product | Project |
| ------- | ------- |
| P1      | PR1     |
| P2      | PR1     |

Now suppose the business rule is:

> A supplier supplies a product to a project whenever all three corresponding relationships exist.

We can represent the relationships using these three tables instead of keeping every three-way combination in one table.

---

# 5. Original Three-Way Table

Suppose the original table is:

| Supplier | Product | Project |
| -------- | ------- | ------- |
| S1       | P1      | PR1     |
| S1       | P2      | PR1     |
| S2       | P1      | PR1     |

This table stores the relationship among:

```text id="2s8k4n"
Supplier
    +
Product
    +
Project
```

If the three-way relationship is completely determined by smaller pairwise relationships, storing all three columns together can introduce unnecessary redundancy.

---

# 6. Decomposition

We can decompose the relationship into:

```text id="7q4j2a"
Supplier_Product
Supplier_Project
Product_Project
```

Conceptually:

```text id="c5v8z1"
             SUPPLIER
             /       \
            /         \
           ↓           ↓
SUPPLIER_PRODUCT    SUPPLIER_PROJECT
           \           /
            \         /
             ↓       ↓
             PRODUCT
                │
                ↓
         PRODUCT_PROJECT
                │
                ↓
             PROJECT
```

The exact decomposition depends on the actual business rules.

That point is very important.

---

# 7. What is 5NF Actually Checking?

5NF asks:

> **Can this table be decomposed further into smaller tables based on valid join dependencies without changing the information represented by the database?**

If yes, and the decomposition is lossless and preserves the intended relationship, further decomposition may be appropriate.

If no useful decomposition exists:

```text id="e4w8px"
The relation may already satisfy 5NF.
```

---

# 8. Lossless Decomposition

One of the most important ideas in 5NF is **lossless decomposition**.

### What does lossless mean?

Suppose we divide one table into smaller tables.

After decomposition, if we join the smaller tables and get back exactly the valid original information, the decomposition is **lossless**.

### Simple idea

```text id="4f7m2c"
Original Table
      ↓
   Decompose
      ↓
Smaller Tables
      ↓
     JOIN
      ↓
Original Information
```

If the join gives the correct information:

```text id="8x5r2v"
✅ Lossless
```

---

# 9. Why Incorrect Decomposition is Dangerous

Suppose we have:

### Supplier-Product

| Supplier | Product |
| -------- | ------- |
| S1       | P1      |
| S1       | P2      |

### Supplier-Project

| Supplier | Project |
| -------- | ------- |
| S1       | PR1     |

### Product-Project

| Product | Project |
| ------- | ------- |
| P1      | PR1     |
| P2      | PR2     |

If we blindly join these tables, we could generate combinations that were **never actually valid**.

For example:

```text id="4f9h8k"
S1 + P2 + PR1
```

might be generated even if the original business relationship did not allow it.

Therefore, decomposition must be based on the actual **join dependency/business rules**.

---

# 10. 5NF vs 4NF

This is an important interview comparison.

| 4NF                                                                 | 5NF                                                                        |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Deals with multivalued dependencies                                 | Deals with join dependencies                                               |
| Removes redundancy caused by independent multi-valued relationships | Removes redundancy caused by complex join relationships                    |
| Usually involves independent relationships                          | Often becomes relevant with relationships involving three or more entities |
| Stronger than BCNF                                                  | Stronger than 4NF                                                          |

### Memory trick

```text id="c1q6m9"
4NF → MULTIVALUED DEPENDENCY
5NF → JOIN DEPENDENCY
```

# 12. SQL Example

5NF is primarily about **database design and relationships**, so the important part is the table decomposition.

## Question

Create a table to store which supplier supplies which product.

### Answer / Query

```sql
CREATE TABLE Supplier_Product
(
    Supplier_ID NUMBER,
    Product_ID  NUMBER
);
```

---

## Question

Create a table to store which supplier is associated with which project.

### Answer / Query

```sql
CREATE TABLE Supplier_Project
(
    Supplier_ID NUMBER,
    Project_ID  NUMBER
);
```

---

## Question

Create a table to store which product is associated with which project.

### Answer / Query

```sql
CREATE TABLE Product_Project
(
    Product_ID NUMBER,
    Project_ID NUMBER
);
```

These tables separately represent the smaller relationships.

The actual decision to decompose a three-way relationship into these tables must come from the **business rules and join dependency**.

---

# 13. Simple Real-Life Analogy

Imagine:

```text
Teacher
Student
Subject
```

A school may record:

> Teacher T1 teaches Student S1 for Subject Java.

If the relationship is truly independent and can be reconstructed from smaller relationships, we might maintain separate relationships such as:

```text
Teacher ↔ Student
Teacher ↔ Subject
Student ↔ Subject
```

But we **cannot automatically assume** that every combination of these three relationships is valid.

That is why 5NF is about **valid join dependencies**, not simply splitting every three-column table.

---

# 14. How to Identify a 5NF Problem

Follow these steps:

### Step 1

Check the lower normal forms:

```text
1NF → 2NF → 3NF → BCNF → 4NF
```

### Step 2

Look for a complex relationship involving multiple entities.

For example:

```text
Supplier + Product + Project
```

### Step 3

Ask:

> Can this relationship be represented correctly using smaller relations?

### Step 4

Join the decomposed relations conceptually.

Ask:

> Does the join recreate exactly the valid original relationship?

If yes:

```text
Lossless decomposition
```

If the decomposition produces invalid combinations or loses valid information:

```text
The decomposition is not appropriate.
```

# 16. Important Point About 5NF

5NF is **much less commonly encountered** in ordinary application database design than 1NF, 2NF, 3NF, and BCNF.

It becomes important when dealing with **complex relationships and join dependencies**.

So for interviews:

### High priority

```text
1NF
2NF
3NF
BCNF
```

### Know the basic concept

```text
4NF
5NF
```

For 5NF, remember:

> **Join Dependency + Lossless Decomposition**

# 17. Common Confusions

### ❌ "5NF means the table must have five columns."

No.

The number **5** refers to the **fifth normal form**, not the number of columns.

---

### ❌ "5NF means we must always split a table into three tables."

No.

Decomposition depends on the actual dependencies and business rules.

---

### ❌ "5NF is just about using JOIN."

No.

SQL `JOIN` is an operation.

**Join Dependency** is a database design concept that describes when a relation can be reconstructed from multiple projections/relations.

---

### ❌ "If a table has three entities, it automatically violates 5NF."

No.

A three-entity relationship does not automatically mean there is a 5NF violation.

There must be a valid **join dependency** that justifies decomposition.

---

**Answer:**

> **Project-Join Normal Form (PJ/NF).**

---

### Q4. What is the main purpose of 5NF?

**Answer:**

> To remove redundancy caused by complex relationships and ensure that further decomposition does not lose information or introduce invalid combinations.

---

### Q5. What is a Join Dependency?

**Answer:**

> A Join Dependency specifies that a relation can be reconstructed by joining multiple decomposed relations.

---

### Q6. What is lossless decomposition?

**Answer:**

> Lossless decomposition means that after decomposing a relation and joining the resulting relations, we can reconstruct the original valid information without loss or incorrect additional information.

---

**Answer:**

> 4NF deals with multivalued dependencies, whereas 5NF deals with join dependencies.
