# 19.11-Complete-Normalisation-Example

Let's understand **normalization from start to finish using one complete example**.

We will take one poorly designed table and gradually transform it through:

```text
Unnormalized Table
        ↓
      1NF
        ↓
      2NF
        ↓
      3NF
        ↓
     BCNF
        ↓
      4NF
        ↓
      5NF
```

The important thing is to understand **what problem is being removed at each stage**.

---

# 1. Starting Table — Unnormalized Data

Suppose a college stores student enrollment information like this:

| Student_ID | Student_Name | Courses      | Department_ID | Department_Name  |
| ---------: | ------------ | ------------ | ------------- | ---------------- |
|        101 | Ravi         | Java, Python | D01           | Computer Science |
|        102 | Anil         | Java         | D01           | Computer Science |
|        103 | Sara         | SQL, Java    | D02           | Mathematics      |

There are several problems here.

### Problem 1 — Multiple values in one cell

For Ravi:

```text
Java, Python
```

are stored in one cell.

For Sara:

```text
SQL, Java
```

are stored in one cell.

This violates the atomicity requirement of **1NF**.

### Problem 2 — Repeated department information

```text
D01 → Computer Science
```

is repeated for Ravi and Anil.

### Problem 3 — Possible update anomaly

If the department name changes, multiple rows may need to be updated.

---

# 2. Step 1 — Convert to 1NF

## Goal of 1NF

> **Every cell should contain a single atomic value.**

Instead of:

| Student_ID | Student_Name | Courses      | Department_ID | Department_Name  |
| ---------: | ------------ | ------------ | ------------- | ---------------- |
|        101 | Ravi         | Java, Python | D01           | Computer Science |

we separate the courses into individual rows.

### 1NF Table

| Student_ID | Student_Name | Course_ID | Course_Name | Department_ID | Department_Name  |
| ---------: | ------------ | --------- | ----------- | ------------- | ---------------- |
|        101 | Ravi         | C01       | Java        | D01           | Computer Science |
|        101 | Ravi         | C02       | Python      | D01           | Computer Science |
|        102 | Anil         | C01       | Java        | D01           | Computer Science |
|        103 | Sara         | C03       | SQL         | D02           | Mathematics      |
|        103 | Sara         | C01       | Java        | D02           | Mathematics      |

Now:

```text
One cell → One value
```

So the atomic-value requirement of **1NF** is satisfied.

---

# 3. Identify the Key

Now we need to identify what uniquely identifies each row.

Consider:

```text id="z7c3px"
Student_ID
```

alone is not unique because Ravi appears for multiple courses.

Similarly:

```text id="w4k9ra"
Course_ID
```

alone is not unique because many students can take the same course.

But:

```text id="m8v2qd"
(Student_ID, Course_ID)
```

can identify a student's enrollment in a course, assuming the same student cannot enroll in the same course more than once.

Therefore:

```text
Composite Key = (Student_ID, Course_ID)
```

---

# 4. Find Functional Dependencies

Now examine what determines what.

### Student information

```text
Student_ID → Student_Name
```

A student's ID determines the student's name.

### Course information

```text
Course_ID → Course_Name
```

A course ID determines the course name.

### Enrollment information

```text
(Student_ID, Course_ID) → enrollment-specific information
```

For example, if we had `Marks`:

```text
(Student_ID, Course_ID) → Marks
```

---

# 5. Step 2 — Convert to 2NF

## Goal of 2NF

> **Remove Partial Functional Dependency.**

Our composite key is:

```text
(Student_ID, Course_ID)
```

But:

```text
Student_ID → Student_Name
```

`Student_Name` depends only on **part of the composite key**.

Similarly:

```text
Course_ID → Course_Name
```

`Course_Name` depends only on another part of the composite key.

Therefore, these are **partial dependencies**.

---

# 6. Decompose into 2NF

Separate student information:

### STUDENT

| Student_ID | Student_Name | Department_ID | Department_Name  |
| ---------: | ------------ | ------------- | ---------------- |
|        101 | Ravi         | D01           | Computer Science |
|        102 | Anil         | D01           | Computer Science |
|        103 | Sara         | D02           | Mathematics      |

Separate course information:

### COURSE

| Course_ID | Course_Name |
| --------- | ----------- |
| C01       | Java        |
| C02       | Python      |
| C03       | SQL         |

And keep the enrollment relationship:

### ENROLLMENT

| Student_ID | Course_ID |
| ---------: | --------- |
|        101 | C01       |
|        101 | C02       |
|        102 | C01       |
|        103 | C03       |
|        103 | C01       |

Now the partial dependencies have been removed from the enrollment relationship.

---

# 7. But There Is Still a Problem

Look at `STUDENT`:

| Student_ID | Student_Name | Department_ID | Department_Name  |
| ---------: | ------------ | ------------- | ---------------- |
|        101 | Ravi         | D01           | Computer Science |
|        102 | Anil         | D01           | Computer Science |
|        103 | Sara         | D02           | Mathematics      |

We have:

```text
Student_ID → Department_ID
```

and:

```text
Department_ID → Department_Name
```

Therefore:

```text
Student_ID → Department_Name
```

through `Department_ID`.

This is a **Transitive Dependency**.

So we need **3NF**.

---

# 8. Step 3 — Convert to 3NF

## Goal of 3NF

> **Remove Transitive Dependency.**

Separate department information.

### STUDENT

| Student_ID | Student_Name | Department_ID |
| ---------: | ------------ | ------------- |
|        101 | Ravi         | D01           |
|        102 | Anil         | D01           |
|        103 | Sara         | D02           |

### DEPARTMENT

| Department_ID | Department_Name  |
| ------------- | ---------------- |
| D01           | Computer Science |
| D02           | Mathematics      |

### COURSE

| Course_ID | Course_Name |
| --------- | ----------- |
| C01       | Java        |
| C02       | Python      |
| C03       | SQL         |

### ENROLLMENT

| Student_ID | Course_ID |
| ---------: | --------- |
|        101 | C01       |
|        101 | C02       |
|        102 | C01       |
|        103 | C03       |
|        103 | C01       |

Now:

```text
Student
   │
   │ Department_ID
   ↓
Department
```

and:

```text
Student
   │
   │ Student_ID
   ↓
Enrollment
   ↑
   │ Course_ID
Course
```

The transitive dependency has been removed from `STUDENT`.

---

# 9. SQL Implementation

## Question

Create the `Department` table.

### Answer / Query

```sql
CREATE TABLE Department
(
    Department_ID   VARCHAR2(10) PRIMARY KEY,
    Department_Name VARCHAR2(50)
);
```

---

## Question

Create the `Student` table and associate each student with a department.

### Answer / Query

```sql
CREATE TABLE Student
(
    Student_ID    NUMBER PRIMARY KEY,
    Student_Name  VARCHAR2(30),
    Department_ID VARCHAR2(10),

    FOREIGN KEY (Department_ID)
        REFERENCES Department(Department_ID)
);
```

---

## Question

Create the `Course` table.

### Answer / Query

```sql
CREATE TABLE Course
(
    Course_ID   VARCHAR2(10) PRIMARY KEY,
    Course_Name VARCHAR2(30)
);
```

---

## Question

Create the `Enrollment` table where a student-course combination is unique.

### Answer / Query

```sql
CREATE TABLE Enrollment
(
    Student_ID NUMBER,
    Course_ID  VARCHAR2(10),

    PRIMARY KEY (Student_ID, Course_ID),

    FOREIGN KEY (Student_ID)
        REFERENCES Student(Student_ID),

    FOREIGN KEY (Course_ID)
        REFERENCES Course(Course_ID)
);
```

---

# 10. What Have We Achieved?

We started with:

```text
One large table
```

and ended with:

```text
STUDENT
   │
   ├──────────────→ DEPARTMENT
   │
   ↓
ENROLLMENT
   ↑
   │
COURSE
```

Instead of repeatedly storing:

```text
Ravi    Computer Science
Anil    Computer Science
```

the department information is stored once.

---

# 11. Where Does BCNF Come In?

3NF is not always the end.

A table can satisfy 3NF but still violate **BCNF**.

### BCNF rule

> For every non-trivial functional dependency `X → Y`, `X` must be a super key.

So after reaching 3NF, we examine the functional dependencies again.

For example:

```text
X → Y
```

Ask:

> Is X a Super Key?

If yes:

```text
✅ BCNF condition satisfied
```

If no:

```text
❌ BCNF violation
```

If a BCNF violation exists, we decompose the relation further.

---

# 12. BCNF in the Complete Process

```text
3NF
 ↓
Check every non-trivial FD
 ↓
Is every determinant a Super Key?
 ↓
YES → BCNF
NO  → Decompose
```

### Important

Do not automatically split every 3NF table.

**Only a genuine BCNF violation justifies further decomposition.**

---

# 13. Where Does 4NF Come In?

After BCNF, we check for **Multivalued Dependencies**.

Suppose a student has independent:

```text
Skills:
Java
Python

Hobbies:
Cricket
Music
```

If these are stored together:

| Student | Skill  | Hobby   |
| ------- | ------ | ------- |
| Ravi    | Java   | Cricket |
| Ravi    | Java   | Music   |
| Ravi    | Python | Cricket |
| Ravi    | Python | Music   |

we have independent multi-valued relationships.

Conceptually:

```text
Student →→ Skill
Student →→ Hobby
```

This can cause unnecessary combinations.

---

# 14. Convert the Example to 4NF

Instead of:

### STUDENT_SKILL_HOBBY

| Student | Skill  | Hobby   |
| ------- | ------ | ------- |
| Ravi    | Java   | Cricket |
| Ravi    | Java   | Music   |
| Ravi    | Python | Cricket |
| Ravi    | Python | Music   |

we separate the independent relationships.

### STUDENT_SKILL

| Student | Skill  |
| ------- | ------ |
| Ravi    | Java   |
| Ravi    | Python |

### STUDENT_HOBBY

| Student | Hobby   |
| ------- | ------- |
| Ravi    | Cricket |
| Ravi    | Music   |

Now we don't need to store every skill-hobby combination.

### 4NF memory

```text
4NF → Remove problematic Multivalued Dependencies
```

---

# 15. Where Does 5NF Come In?

After 4NF, we can check for **Join Dependencies**.

Suppose there is a complex relationship involving:

```text
SUPPLIER
PRODUCT
PROJECT
```

and the business rules allow the relationship to be represented correctly by smaller relations.

For example:

```text
SUPPLIER_PRODUCT
SUPPLIER_PROJECT
PRODUCT_PROJECT
```

If the original valid relationship can be reconstructed **without losing valid information or generating invalid combinations**, the decomposition is lossless.

This is the area addressed by **5NF**.

---

# 17. One Example for Each Normal Form

| Stage            | Problem                               | Solution                                                |
| ---------------- | ------------------------------------- | ------------------------------------------------------- |
| **Unnormalized** | Multiple values in one cell           | Start normalization                                     |
| **1NF**          | Non-atomic/repeating data             | Make values atomic                                      |
| **2NF**          | Partial dependency                    | Separate attributes depending on parts of composite key |
| **3NF**          | Transitive dependency                 | Separate non-key-to-non-key dependencies                |
| **BCNF**         | Determinant is not a super key        | Decompose affected relation                             |
| **4NF**          | Independent multivalued relationships | Separate multivalued relationships                      |
| **5NF**          | Join dependency                       | Decompose based on valid lossless join dependencies     |

# 18. Complete SQL Retrieval Example

After normalization, information is distributed across tables.

## Question

Display each student's name, department name, and course name.

### Answer / Query

```sql
SELECT s.Student_Name,
       d.Department_Name,
       c.Course_Name
FROM Student s
JOIN Department d
    ON s.Department_ID = d.Department_ID
JOIN Enrollment e
    ON s.Student_ID = e.Student_ID
JOIN Course c
    ON e.Course_ID = c.Course_ID;
```

### Output

| Student_Name | Department_Name  | Course_Name |
| ------------ | ---------------- | ----------- |
| Ravi         | Computer Science | Java        |
| Ravi         | Computer Science | Python      |
| Anil         | Computer Science | Java        |
| Sara         | Mathematics      | SQL         |
| Sara         | Mathematics      | Java        |

This is an important point:

> **Normalization does not mean we lose the ability to see the complete information.**

The information is stored separately, and `JOIN` allows us to retrieve it together.

---

# 19. Why Did We Split the Tables?

The decomposition is based on **what the data depends on**.

### Student information

```text
Student_ID → Student_Name
```

So:

```text
STUDENT
```

### Department information

```text
Department_ID → Department_Name
```

So:

```text
DEPARTMENT
```

### Course information

```text
Course_ID → Course_Name
```

So:

```text
COURSE
```

### Enrollment information

```text
(Student_ID, Course_ID) → Enrollment-specific data
```

So:

```text
ENROLLMENT
```

This is the heart of normalization.

---

# 20. What Happens If We Don't Normalize?

Suppose everything remains in one table:

| Student_ID | Student_Name | Course_ID | Course_Name | Department_ID | Department_Name  |
| ---------: | ------------ | --------- | ----------- | ------------- | ---------------- |
|        101 | Ravi         | C01       | Java        | D01           | Computer Science |
|        101 | Ravi         | C02       | Python      | D01           | Computer Science |
|        102 | Anil         | C01       | Java        | D01           | Computer Science |

We get repeated information:

```text
Ravi
Computer Science
D01
Java
```

and so on.

This can lead to:

```text
Insert Anomaly
Update Anomaly
Delete Anomaly
```

Normalization helps us organize the data to reduce these problems.

---

# 21. Normalisation Does Not Mean "Split Everything"

This is extremely important.

The goal is **not**:

```text
One table
   ↓
100 tables
```

The goal is:

```text
Understand dependencies
        ↓
Identify redundancy/problems
        ↓
Decompose when justified
        ↓
Maintain correct relationships
```

A good database design balances:

* Data integrity
* Redundancy
* Query requirements
* Performance
* Maintainability

# 23. Interview Questions

### Q1. Explain normalization with an example.

**Answer:**

> Suppose a single student table stores student, course, and department information together. This can cause redundancy and anomalies. In 1NF we make values atomic, in 2NF we remove partial dependencies, in 3NF we remove transitive dependencies, BCNF ensures every determinant is a super key, 4NF deals with multivalued dependencies, and 5NF deals with join dependencies.

---

### Q2. What happens in 1NF?

> Repeating groups and multiple values in a cell are removed, resulting in atomic values.

### Q3. What happens in 2NF?

> Partial functional dependencies are removed.

### Q4. What happens in 3NF?

> Transitive functional dependencies are removed.

### Q5. What happens in BCNF?

> Every determinant of a non-trivial functional dependency must be a super key.

### Q6. What happens in 4NF?

> Problematic multivalued dependencies are removed.

### Q7. What happens in 5NF?

> Problematic join dependencies are handled through appropriate lossless decomposition.

---

# 24. Interview-Ready Answer

> **Normalization is the process of organizing database data into properly related tables to reduce redundancy and avoid anomalies. Starting from an unnormalized table, 1NF makes values atomic, 2NF removes partial dependencies, 3NF removes transitive dependencies, BCNF ensures every determinant is a super key, 4NF handles multivalued dependencies, and 5NF handles join dependencies. The goal is to store each fact in an appropriate place while preserving the ability to reconstruct the required information through relationships and joins.**
