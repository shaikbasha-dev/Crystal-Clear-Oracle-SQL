# 19.10-Normalisation-vs-Denormalisation

## 1. What is Normalisation?

**Normalisation** is the process of organizing data into properly structured tables to:

* Reduce unnecessary data repetition.
* Reduce redundancy.
* Avoid insert, update, and delete anomalies.
* Maintain data consistency.

We progressively use normal forms such as:

```text
1NF → 2NF → 3NF → BCNF → 4NF → 5NF
```

### Simple idea

> **Normalisation = Split data into appropriate related tables.**

---

# 2. What is Denormalisation?

**Denormalisation** is the process of intentionally combining or repeating some data in tables to improve **data retrieval performance**.

Instead of always joining several tables, some information may be stored together.

### Simple idea

> **Denormalisation = Intentionally keep some redundancy to make reading data faster or simpler.**

---

# 3. Simple Example

Suppose we have:

### STUDENT

| Student_ID | Student_Name | Department_ID |
| ---------: | ------------ | ------------- |
|        101 | Ravi         | D01           |
|        102 | Anil         | D01           |

### DEPARTMENT

| Department_ID | Department_Name  |
| ------------- | ---------------- |
| D01           | Computer Science |

This is a normalized design.

To display the student and department name together, we use a `JOIN`.

---

## Question

Display each student's name and department name.

### Answer / Query

```sql
SELECT s.Student_Name,
       d.Department_Name
FROM Student s
JOIN Department d
ON s.Department_ID = d.Department_ID;
```

### Output

| Student_Name | Department_Name  |
| ------------ | ---------------- |
| Ravi         | Computer Science |
| Anil         | Computer Science |

This design avoids repeating:

```text
Computer Science
```

for every student.

---

# 4. What Would Denormalisation Do?

In a denormalized design, we might store:

### STUDENT

| Student_ID | Student_Name | Department_ID | Department_Name  |
| ---------: | ------------ | ------------- | ---------------- |
|        101 | Ravi         | D01           | Computer Science |
|        102 | Anil         | D01           | Computer Science |

Now the department name is repeated.

The advantage is that the application can retrieve the student's department name directly without performing the `JOIN`.

But the disadvantage is that the same information is stored multiple times.

---

# 5. Normalisation vs Denormalisation

| Normalisation                                         | Denormalisation                                    |
| ----------------------------------------------------- | -------------------------------------------------- |
| Organizes data into separate related tables           | May combine tables or intentionally duplicate data |
| Reduces redundancy                                    | Accepts some redundancy                            |
| Helps avoid anomalies                                 | May reintroduce some redundancy/anomaly risks      |
| Improves data consistency                             | Can make consistency harder to maintain            |
| Usually requires more `JOIN`s for related information | Can reduce the number of `JOIN`s                   |
| Focuses on good data organization                     | Often focuses on read performance                  |
| Common in transactional systems                       | Often useful in read-heavy/reporting scenarios     |

---

# 6. Main Difference

The simplest way to understand the difference:

```text
NORMALISATION
      ↓
Reduce redundancy
      ↓
Separate related data
      ↓
More JOINs may be required
```

Whereas:

```text
DENORMALISATION
      ↓
Accept some redundancy
      ↓
Keep related data together
      ↓
Fewer JOINs may be required
```

---

# 7. Advantages of Normalisation

### 1. Reduces data redundancy

The same information does not need to be stored repeatedly.

### 2. Reduces anomalies

It helps avoid:

```text
Insert Anomaly
Update Anomaly
Delete Anomaly
```

### 3. Improves data consistency

When information is stored in one appropriate location, updating it is easier and less error-prone.

### 4. Better database structure

Different entities can be stored in appropriate tables.

For example:

```text
STUDENT
COURSE
DEPARTMENT
PROFESSOR
```

instead of putting everything into one large table.

---

# 8. Disadvantages of Normalisation

### 1. More tables

Normalization can result in many tables.

### 2. More JOINs

To retrieve related information, multiple tables may need to be joined.

### 3. Complex queries

Queries can become more complex when information is spread across several tables.

### 4. Read performance can sometimes be affected

For some workloads, repeatedly joining many tables can be more expensive than reading pre-combined data.

---

# 9. Advantages of Denormalisation

### 1. Faster reads in suitable workloads

Some queries can retrieve information without performing many joins.

### 2. Fewer JOINs

Related information may already be available in the same table.

### 3. Simpler reporting queries

For certain reporting or analytical workloads, keeping frequently used information together can simplify queries.

### 4. Can improve read performance

This is especially useful when the database performs many reads and comparatively fewer updates.

---

# 10. Disadvantages of Denormalisation

### 1. Data redundancy

The same information may be stored in multiple places.

Example:

```text
Computer Science
Computer Science
Computer Science
```

### 2. Update problems

If the department name changes, every duplicated occurrence may need to be updated.

### 3. Data inconsistency

If one occurrence is updated but another is not, different values can exist for the same information.

### 4. More storage

Repeated data consumes additional storage.

---

# 11. Example: Normalised Design

Suppose:

| Student_ID | Student_Name | Department_ID |
| ---------: | ------------ | ------------- |
|        101 | Ravi         | D01           |
|        102 | Anil         | D01           |
|        103 | Sara         | D02           |

And:

| Department_ID | Department_Name  |
| ------------- | ---------------- |
| D01           | Computer Science |
| D02           | Mathematics      |

Here:

```text
Student
   │
   │ Department_ID
   ↓
Department
```

Department information is stored once.

---

# 12. Example: Denormalised Design

Instead, we could store:

| Student_ID | Student_Name | Department_ID | Department_Name  |
| ---------: | ------------ | ------------- | ---------------- |
|        101 | Ravi         | D01           | Computer Science |
|        102 | Anil         | D01           | Computer Science |
|        103 | Sara         | D02           | Mathematics      |

Now the department name is repeated.

The advantage:

```text
Student → Department Name
```

can be retrieved directly.

The disadvantage:

```text
Department_Name
       ↓
Repeated in multiple rows
```

---

# 13. When Should We Use Normalisation?

Normalisation is generally useful when:

* Data consistency is important.
* There are frequent `INSERT`, `UPDATE`, and `DELETE` operations.
* We want to minimize redundancy.
* The database is transaction-oriented.
* We want clear relationships between entities.

### Simple memory

> **Frequent changes + consistency → Normalisation is valuable.**

---

# 14. When Can Denormalisation Be Useful?

Denormalisation can be useful when:

* Read performance is very important.
* The system performs many queries but relatively fewer updates.
* Complex joins are a performance bottleneck.
* Reporting or analytical queries frequently need the same combined information.
* Some controlled redundancy provides a practical performance benefit.

### Simple memory

> **Read performance + fewer joins → Denormalisation may be useful.**

---

# 15. Is Denormalisation Bad?

**No.**

Denormalisation is not automatically bad database design.

It is a **deliberate design decision**.

The important point is:

> We should not introduce redundancy without a reason.

A common approach is:

```text
First design a properly normalized database
             ↓
Identify actual performance problems
             ↓
Measure the workload
             ↓
Denormalise selectively if justified
```

---

# 16. Normalisation and Denormalisation Together

They are not necessarily enemies.

A real database can use a mixture of both approaches.

For example:

```text
Core transactional data
        ↓
   Normalised
        ↓
   Good consistency

Reporting / read-heavy requirements
        ↓
Selective denormalisation
        ↓
   Faster access
```

---

# 17. Important Interview Difference

### Question

**What is the difference between normalization and denormalization?**

### Answer

> **Normalization organizes data into multiple related tables to reduce redundancy and improve consistency, while denormalization intentionally introduces some redundancy or combines data to reduce joins and potentially improve read performance.**

---

# 18. Common Confusions

### ❌ "Normalization means creating as many tables as possible."

No.

The goal is **proper organization**, not creating unnecessary tables.

---

### ❌ "Denormalization means bad database design."

No.

Denormalization can be appropriate when there is a legitimate performance or reporting requirement.

---

### ❌ "Normalization always makes queries faster."

No.

Normalization can reduce redundancy and improve consistency, but retrieving related data may require more joins.

---

### ❌ "Denormalization always makes the database faster."

No.

It can improve some read-heavy workloads, but it increases redundancy and can make writes and consistency management more difficult.

---

# 19. Interview Questions

### Q1. What is normalization?

> Normalization is the process of organizing data into properly structured related tables to reduce redundancy and avoid data anomalies.

### Q2. What is denormalization?

> Denormalization is the intentional introduction of some redundancy or combining of data to improve performance or simplify certain read operations.

### Q3. Why is normalization used?

> To reduce redundancy, improve consistency, and prevent insert, update, and delete anomalies.

### Q4. Why is denormalization used?

> Mainly to reduce joins and improve performance for suitable read-heavy workloads.

### Q5. Does denormalization increase redundancy?

> Yes. Intentional redundancy is one of its characteristics.

### Q6. Which approach generally uses more JOINs?

> **Normalization**, because related information is distributed across separate tables.

### Q7. Which approach can reduce JOINs?

> **Denormalization.**

### Q8. Is denormalization always required?

> No. It should be used only when the benefits justify the additional redundancy and maintenance cost.

---

# 20. Interview-Ready Answer

> **Normalization organizes data into multiple related tables to reduce redundancy, improve consistency, and prevent anomalies. Denormalization intentionally introduces some redundancy or combines data to reduce joins and improve read performance when necessary. Normalization is generally preferred for maintaining data integrity, while denormalization can be applied selectively for performance or reporting requirements.**
